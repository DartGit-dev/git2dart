# reversa-spec-sdd, Spec-Driven Development no Reversa

This skill drives the complete SDD process within the Code New Project Agents pipeline: **decompose → write → evaluate → iterate** until each spec is ready for the forward cycle.

The skill is a vendored version of the global `sdd-spec`, adapted for the Reversa context: it reads `prd.md` as the primary source, writes to `reversa/sdd/sdd/`, marks everything with a seal 🟡 and ends with a handoff to `/reversa-forward`.

## Por que SDD?

Specs written before code save time because:

- Make ambiguities visible before they become bugs
- Align expectations between those who ask and those who implement
- Serve as a permanent reference for testing, reviews and onboarding
- Allow LLMs to implement with much more precision

The methodology here is **Pragmatic RFC plus LLM-First**: structured like an RFC (Problem / Goals / Design / Edge Cases), but optimized to be consumed by humans and AI agents.

## Before you start

1. Read `.reversa/state.json` to `user_name`, `chat_language`, `doc_language`, `output_folder` (default `reversa/sdd`).
2. Check precondition: **`<output_folder>/prd.md` must exist**. If absent, close with a clear message:
> "I didn't find `<output_folder>/prd.md`. Run `/reversa-drafter` first, or invoke `/reversa-new` to drive the complete pipeline."
3. Ensure that the `<output_folder>/sdd/` folder exists. Create if absent.

## Default output path

Each spec generated goes to:

```
<output_folder>/sdd/<component-kebab-case>.md
```

For example: `reversa/sdd/sdd/user-authentication.md`, `reversa/sdd/sdd/payment-checkout.md`.

The component is decomposed from `prd.md` in the first phase.

## Seal 🟡 mandatory

All items in specs generated by `reversa-spec-sdd` must use the **🟡 PLANNED** seal (variant of 🟡 INFERRED used in other Reversa contexts). The 🟢 CONFIRMED seal is reserved for facts extracted from existing code by the Discovery Team, an inherited rule to avoid confusion between "legacy fact" and "forward hypothesis".

Each spec requirement, behavior, edge case and acceptance criteria must begin with 🟡.

## Fluxo de trabalho

### Phase 0, Decomposition into components

Read `<output_folder>/prd.md` in full. From the "Scope", "Target Personas" and "Acceptance Criteria" sections, propose a decomposition of the product into logical components. Each component must represent a cohesive unit that will become an individual SDD spec.

Present the decomposition to the user:

> "Through PRD, I identified these logical components:
>
> 1. **<component 1>**: <one sentence description>
> 2. **<component 2>**: <one sentence description>
>   3. **<component N>**: ...
>
> Do you agree with this decomposition? Do you want to add, remove or rename any?"

Wait for response. Iterate until confirmation (maximum 2 adjustments). For each committed component, normalize the name in ASCII kebab-case.

### Phase 1, Interview by component (optional)

For each component, decide whether the information in `prd.md` is enough:

- **Enough:** go straight to Phase 2.
- **Missing:** ask a maximum of 3 focused questions, covering the points below that are missing:
1. **The specific problem for that component:** "What role does `<component>` play in the product?"
2. **The success:** "How will you know this component worked? What can the user do?"
3. **Scope:** "What is explicitly OUTSIDE the scope of this component?"
4. **Edge cases:** "Are you able to anticipate difficult cases or error situations in this component?"

Total limit: 3 questions per component, choosing the most critical ones.

### Phase 2, Write the spec

Use the template in `references/spec_template.md` as a base. Complete **all** sections:

- **Functional requirements:** format `RF-01`, `RF-02`. Each testable in isolation. Mandatory 🟡 seal.
- **Behaviors:** describe what happens, not how to implement it. The spec defines the **what**, not the **how**.
- **Zero ambiguity:** if you are not sure, mark it with `⚠️ ABERTO:` and add it to the Open Questions list.
- **LLM-readiness:** write as if a developer or LLM would implement it without asking anything.
- **Seal 🟡 on all spec items**, including RFs, edge cases, criteria.

Use `<doc_language>` in spec content.

### Phase 3, Automatic quality assessment

After writing each spec, run the scorer.

**Python Detection:** try `python --version` or `python3 --version` via shell.

- **If Python available:**

  ```
  python scripts/spec_scorer.py --spec <output_folder>/sdd/<component>.md
  ```

Use the literal output of the script.

- **If Python is not available (manual mode):** apply the procedure in the section "Scoring in engines without Python" below.

O scoring retorna:

- **Total score** (0 to 100) with breakdown by dimension
- **Critical gaps** that need resolution
- **Suggestions** ordered by impact

Evaluated dimensions (see `references/evaluation_rubric.md` for details):

| Dimension | Weight | What do you rate |
|---|---|---|
| Completeness | 30% | All sections completed, requirements covered |
| Testability | 25% | Verifiable requirements, clear acceptance criteria |
| Clarity | 20% | Lack of ambiguities, precise language |
| Escopo | 15% | Non-goals definidos, limites claros |
| Edge Cases | 10% | Error cases and system limits covered |

### Phase 4, Iteration

Based on the score:

1. Score **≥ 80**: spec ready. Persist and move on to the next component.
2. Score **60 to 79**: correct obvious gaps automatically, then confirm with the user if anything critical was missing. Redo scoring.
3. Score **< 60**: return to Phase 1 with questions focused on the gaps. Redo scoring.

Limit: **3 iterations per component**. After 3 attempts, persist with the current score and add a `## Quality Issues` section to the file.

At each iteration, show the delta: "rose from 54 to 71, 2 critical gaps missing".

### Phase 5, Persistence and handoff

For each completed component:

1. Write `<output_folder>/sdd/<component-kebab-case>.md` with atomic writing (tempfile plus rename), UTF-8 without BOM.
2. Include the **evaluation report** (score + gaps + suggestions) at the end of the file.
3. If the file already exists, ask the user if they want to overwrite it.

After generating **all** specs, display the consolidated report:

> "`<user_name>`, SDD generation completed. Specs created in `<output_folder>/sdd/`:
>
> | Component | Path | Score | Iterations |
> |---|---|---|---|
> | <comp1> | <output_folder>/sdd/<comp1>.md | 87 | 1 |
> | <comp2> | <output_folder>/sdd/<comp2>.md | 73 | 2 |
> | <comp3> | <output_folder>/sdd/<comp3>.md | 68 | 3 (with pending issues) |
>
> All items marked with seal 🟡 (planned).
>
> Next step: run `/reversa-forward`, which will consume these specs and start the evolution cycle until the code.
>
> Type **CONTINUE** to start `/reversa-forward`, or pause here."

Never proceed automatically.

## Scoring in engines without Python

When `python --version` and `python3 --version` fail, activate manual mode:

1. **Read `references/evaluation_rubric.md`** for the criteria for each dimension.
2. For each of the 5 dimensions, evaluate the spec mentally and assign a score from 0 to 100, justifying in 1 to 2 sentences:

- **Completeness (30%):** all 9 mandatory sections completed? Do RFs cover the stated scope?
- **Testability (25%):** Are RFs verifiable in isolation? Do acceptance criteria have a Given/When/Then format or equivalent?
- **Clarity (20%):** are there vague phrases (intuitive, quick, easy)? Are there contradictions?
   - **Escopo (15%):** non-goals declarados explicitamente? Limites claros?
- **Edge cases (10%):** at least 3 error/edge cases covered?

3. **Calcule o score ponderado:**

   ```
   score = (Completude * 0.30) + (Testabilidade * 0.25) + (Clareza * 0.20)
         + (Escopo * 0.15) + (Edge Cases * 0.10)
   ```

4. **List the gaps** in order of criticality (blockers, important, improvements).

5. **Render the output** in the same format as the script:

   ```
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   SCORE TOTAL: <NN>/100
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

   Breakdown:
     Completude:    <NN>/100 (peso 30%)
     Testabilidade: <NN>/100 (peso 25%)
     Clareza:       <NN>/100 (peso 20%)
     Escopo:        <NN>/100 (peso 15%)
     Edge Cases:    <NN>/100 (peso 10%)

Critical gaps:
     - <gap 1>
     - <gap 2>

Suggestions (by impact):
1. <suggestion>
2. <suggestion>
   ```

The result in manual mode must be equivalent to that of the script for the same spec.

## Mode: evaluation of existing spec

If the user invokes `/reversa-spec-sdd` outside of the `/reversa-new` pipeline, with a spec already written for evaluation:

1. Ask for the file path.
2. Perform scoring (script or manual).
3. Present score with detailed analysis by dimension.
4. List gaps in order of criticality.
5. Ask if you want you to correct the points made.

This mode does not require `prd.md` or enter the pipeline. It is a separate utility inherited from the original skill.

## Signs of a bad spec (avoid)

- Requirements that cannot be tested ("the system must be intuitive")
- Missing or vague scope section ("let's see what makes sense")
- Mix technical implementation design with expected behavior
- Contradictory requirements not flagged
- No defined acceptance criteria
- Edge error cases completely absent

## Signs of a good spec (search)

- Any developer can implement without asking questions
- Any QA can write tests from it
- Non-goals are as clear as goals
- Error cases have defined behavior
- Each requirement has a unique traceable ID
