## Project configuration

```yaml
closure_policy: {{CLOSURE_POLICY}}   # local-software | package | production-service
control_mode: gated                  # supervised | gated | autonomous
```

- `closure_policy` define o que "resolvido" exige:
- `local-software`: regression tests passing + spec verdict
- `package`: previous + merge + fixed version published (+ backports required)
- `production-service`: previous + delivery + observation window without recurrence
- `control_mode: gated` (default): reading, isolated playback and diagnosis flow without approval;
mandatory gate to apply tests, apply change set, change effective spec, use harness
external with access to the project and any destructive operations.

## Estrutura

Bugs are grouped by **context** (feature, module or use case, in the language of the person reporting). Each context is an aggregator folder with EVERYTHING in that area: bugs, inspections and views. The folder is created on demand, when the first problem in the area is reported; nothing is created empty.

```text
reversa/bugs/
├── README.md this contract
├── taxonomy.yaml controlled area/module/feature vocabulary
└── <context>/ e.g.: credit-system/, shopping-cart/
├── bugs/BUG-<data>-<suffix>-<slug>/ single bug folder (IMMUNTABLE address, never moves)
│ ├── bug.md canonical record
    │   ├── evidence/  ├── debate/  └── fix/
├── inspections/<scan>/ context fine-tooth comb reports
└── generated/ views of the context, regenerated by /reversa-debugger-graph
```

## Ciclo de vida

`status`: `open` → `active` → `resolved`. `phase` details the step within `active`
(mitigating, reproducing, diagnosing, testing, patching, delivering, observing, awaiting-human).
Blocking is a condition (`blocking:`), never a status. Every closure has `resolution_kind`.

**Completion lock:** when satisfying the closure policy, the bug receives `DONE.md` in the folder and becomes
READ ONLY for all agents. Reopening: consciously remove the lock, or register a
new bug with `regression-of`. The list of blocked items appears in the context's `graph.html` (view
derived, without manual editing).

## Traceability rule

Every bug MUST identify:

1. The spec section that defines the expected behavior (effective spec = original + current addenda).
Without spec, the bug carries the label `spec-gap` and the gap is addressed before resolution.
2. The affected code (where it appears) and, after investigation, the root cause (where it was born), with status
epistemological and evidence.
3. Reproduction and regression testing.

A bug CANNOT be `resolved: fixed` with `traceability.specs`, `root_cause` (confirmed) or
`regression_tests` vazios.

## Agent protocol

1. Register (`/reversa-debugger`) NEVER fixes it. Fix (`/reversa-debugger-fix`) follows two gates of
pass with diff (tests that fail; change set that makes tests pass).
2. The original spec is NEVER edited. Spec change becomes versioned and immutable addendum
`<output_folder>/addenda/bug-<ID>-vNNN.md`, with human decision recorded.
3. Diff of the code and diff/adendo of the spec are registered TOGETHER in the bug Resolution.
4. Bugs with `visibility: restricted` are outside the views and nothing exploitable goes to the external harness.
5. Relationship and root cause have epistemological status: hypothesis is not fact.

## Conventions

- Canonical ID: `BUG-<YYYYMMDD>-<sufixo>` (merge-safe). `display_number` is human nickname.
- References always by ID; views resolve the path.
- Evidence in `evidence/`, never giant logs within Markdown.
- Complete scheme: see `bug-schema` in the Reversa (agents/reversa-debugger/references/) documentation.
